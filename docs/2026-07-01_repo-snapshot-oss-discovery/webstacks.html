Full-stack web apps · a shared map for two people

Web stacks, design, and where they meet

Three things in one place: an honest review of the stacks running every web app in this repo, a plain-language map of the options that exist, and — the part that matters most — how design and UX choices intersect with the technical stack you pick. Written for two readers at once.

Reader A

AI-first builder Randy

Building a serious AI-coding operation since ChatGPT launched, with rising sophistication and new tools. Not a professional engineer, doesn't read or write code, and won't. Directs AI to build; decides at the product and PR level. Needs to understand the tradeoffs of a stack without touching the code inside it.

Reader B

UX / design lead the designer

A professional UX and web-design lead from big tech, small-teams, full-process — but from before AI let designers ship real prototypes in code and let engineers design with AI tools. Knows design systems, handoff, and craft cold; needs the map of how that expertise lands in an AI-era stack.

Throughout, R marks a note aimed at Randy and D a note aimed at the designer. The whole point is that you end up with one shared vocabulary — so a conversation about "which stack for this app" is also a conversation about "how far can the design go, and who can change it."

01 · The review

What's running in the repo right now

Every web-facing app, verified from the actual files on 2026-07-01. The surprise: you're already well past "just Webflow." The repo spans five distinct patterns and three deploy targets (AWS Lambda, AWS S3/CloudFront via CDK, and Fly containers). That's a broader, more modern footprint than most solo operators — and also the thing worth consolidating.

A · Webflow front + AWS serverless back

QRAG (production-like, real users). Front end is Webflow — designer plus AI-managed custom-code blocks (shells in web-shared/webflow/, app code in apps/qrag/web/). Back end is AWS Chalice Lambdas (qrag-llm, qrag-routing, vrag-llm) on API Gateway, Pinecone vectors, S3 context, JWT + HMAC PII hashing.

  • Good: real design polish without code; battle-tested backend.
  • Friction: design lives in a tool AI can't cleanly drive; front/back split across two worlds.

B · Static site (SSG) + AWS CDK

focusonfoundations.org redo (branch). Astro 5, static output, plain .astro components + vanilla JS modules ported off Webflow (marked, validator) — no Tailwind, no React islands yet. Infra is AWS CDK (TypeScript, aws-cdk-lib 2.15) provisioning an S3 + CloudFront static site with staging/prod deploy scripts.

  • Good: you now own the whole deploy; fast, cheap, SEO-friendly.
  • Gap: no design system yet (add Tailwind + components to raise the ceiling).

C · Containerized Python web app on Fly

lesson-logger dashboard (fof-lesson-dash) and the Hermes services. FastAPI + uvicorn + Jinja2 templates, static CSS, in a Dockerfile deployed to Fly.io, SQLite synced from Hermes. This is your "own the full stack in a container" goal already realized for internal tools.

  • Good: one owned box, server-rendered, simple, AI-easy to extend.
  • Ceiling: Jinja templates cap design sophistication unless paired with Tailwind/components.

D · Local FastAPI + vanilla-JS tools

prism-sync (FastAPI shelling to ssh/rsync, vanilla HTML/CSS/JS matrix UI, TOML config, localhost:8770) and the MathQuest control panel (HTTP panel on 8765). Utilities you run on your own machine, not deployed.

  • Good: zero-ceremony, fast to build, disposable.
  • Scope: personal tools — design ambition is deliberately low.

E · Framework-less static (HTML/JS + WASM/WebGL)

math-quiz (multi-page HTML/JS, SQLite in the browser via sql-wasm.wasm, Playwright tests, a local Python dev server), the kid games (apps/games/: robopoli, Three.js experiments, 3D viewers), and family apps (Kid1, milestone-web).

  • Good: runs anywhere, no build step, no server; great for kids' apps and 3D.
  • Ceiling: hand-rolled UI; consistency and design system are manual.

Also present

Shared AWS Lambdas (hash-store, hmac-hash, send-email); the voice-router dashboard (design-variant phase); animation-studio (Python + vision-verifier loop). The cross-app Webflow shells in web-shared/webflow/ are the connective tissue of the Webflow-era apps.

02 · The landscape

The option space, in plain language

A full-stack web app is a stack of decisions. Here are the layers and the realistic choices at each, with the tradeoffs that actually matter for a small AI-first operation. You don't need all of it — you need to recognize the names and what each buys you.

Layer 1 · Rendering model — how the page reaches the browser

Static (SSG)

Pages built once, served as files. Fastest, cheapest, most secure. Best for content/marketing sites. Astro, plain HTML

Single-page app (SPA)

One HTML shell, JS renders everything client-side. Rich interactivity; weaker SEO/first-load. React, Svelte, Vue

Server-rendered (SSR)

Server builds each page per request. Good SEO + dynamic data. Needs a running server. Next, SvelteKit, FastAPI+Jinja

Islands / hybrid

Static page with small interactive "islands." Best of both for content-with-some-app. Astro islands, HTMX

D This is the axis you already think in as "marketing site vs product." R Your repo already has one of each: Astro (static), QRAG (SPA-ish), lesson-dash (SSR).

Layer 2 · Frontend framework — the tool the UI is written in

Astro

Content-first, ships almost no JS, can embed React/Svelte islands. Ideal for sites and docs. You already use it.

Next.js (React)

The default for interactive apps. Biggest ecosystem, best AI training coverage, works with shadcn/ui. Heavier.

SvelteKit

Simpler mental model, less boilerplate, excellent DX. Smaller ecosystem than React but very AI-friendly.

Vanilla + Web Components / HTMX

No framework. HTMX adds interactivity via HTML attributes + a server. Lowest ceremony; lower design-system leverage.

Layer 3 · Styling & UI system — where design actually lives

Tailwind CSS

Utility classes = a design system encoded in config (spacing, color, type scales). The current default, and the format AI generates best.

shadcn/ui

Copy-in React components (built on Radix) you own and restyle. Accessible, unopinionated look. The modern app-UI default.

DaisyUI

Tailwind component classes with themes — fast, good-looking defaults, framework-agnostic. Lightest path to "looks designed."

Radix / MUI / Chakra

Component libraries — Radix (unstyled+accessible), MUI (Material, batteries-included), Chakra (friendly defaults).

D This is the layer that changed the most. Pre-AI, the design system lived in Figma and got hand-translated. Now it lives in code as tokens + components (Tailwind config, shadcn variants) that both you and the AI read and write. Your design-system craft doesn't disappear — it moves from "Figma library + redlines" to "token definitions + component contracts + review." R Picking Tailwind + a component library is the single biggest lever for "AI produces good-looking UI by default."

Layer 4 · Backend, data & auth

Serverless functions

AWS Lambda/Chalice, Cloudflare Workers, Vercel funcs. Scale-to-zero, pay-per-use. Your QRAG backend.

Long-running server

FastAPI / Express / Hono in a container. Simple mental model, always-on. Your Fly dashboards.

Backend-as-a-service

Supabase (Postgres + auth + storage), Firebase. Skip building a backend; great for prototypes and small apps.

Data + auth

Postgres (relational), SQLite (single-file, great for small apps), vector DB (Pinecone/pgvector for RAG). Auth via Clerk/Auth.js/Supabase or your JWT+HMAC.

Layer 5 · Hosting & deploy

Managed frontend hosts

Vercel, Netlify, Cloudflare Pages. Push-to-deploy, previews, CDN. Vercel is easiest but cost-scales unfavorably (your noted concern).

Container platforms

Fly.io (you use it), Railway, Render. Deploy a Docker image; own the runtime; predictable cost. Great middle ground.

AWS (owned)

S3+CloudFront (static, via CDK — you use it), Lambda (serverless), EC2/ECS (containers). Most control, most complexity.

Cloudflare

Pages + Workers + D1/R2. Cheap at scale, edge-first. A strong Vercel alternative worth evaluating.

03 · The point of all this

Where design choices meet stack choices

The core idea in one sentence: your stack decides how far the design can go and who is able to change it. Two questions capture the whole intersection — how high is the design ceiling out of the box, and how well can an AI agent (not a human coder) drive it while you still own the deploy. Plot the stacks on those two axes and the decision becomes visual.

App framework (Next/SvelteKit) Static site (Astro) Server-rendered Python No-code (Webflow) Framework-less / 3D

Hover any point for the read. X → design & UX ceiling (how sophisticated the look, interaction, and motion can get with reasonable effort). Y → AI-drivability & ownership (how cleanly an AI agent can generate and change it, and how fully you own the deploy). The upper-right quadrant is the sweet spot for an AI-first operator; Webflow sits high-design but low-AI-drive — precisely why it's on your way out.

The three insights that fall out of the map

1 · Tailwind + a component library is the bridge. It's what moves a stack rightward (higher design ceiling) and upward (more AI-drivable) at the same time — because the design system becomes legible code that AI generates fluently. Adding it to your Astro site and your Fly dashboards is the highest-leverage single move.

2 · Webflow's tradeoff is now backwards for you. It buys design polish by putting design in a place AI can't reach and you don't own. In an AI-first shop, that's the expensive corner — you give up drivability and ownership for polish you can now get in code.

3 · Match the stack to the app's design ambition, not the other way around. A kids' math game doesn't need Next.js; a client-facing product shouldn't ship as hand-rolled HTML. The map is a triage tool: place the app by how much design and interactivity it truly needs, then read off the stack.

04 · Same map, two vantage points

What this means for each of you

For the UX / design lead

D Your craft moved layers — it didn't shrink

  • The design system is now code. Tokens (color, type, spacing), component variants, and states live in Tailwind config + a component library, not only in Figma. You define the contract; AI fills in the implementation. Learn to read/spec tokens and component APIs — that's the new handoff.
  • Prototypes are real now. Tools like v0, Lovable, Bolt, and Claude artifacts turn your design intent into working code. Your prototype can be the spec — no more redlines lost in translation.
  • Your scarce value rose. AI does adequate UI; it does not do taste, systems thinking, information architecture, motion, or accessibility at your level. Those are exactly the things that don't come free with any stack — so they're where you lead.
  • Figma → code paths exist (Figma Make, Anima, Builder.io Visual Copilot) but the durable pattern is design tokens as the shared source of truth (W3C tokens, Style Dictionary) that both Figma and the codebase consume.
  • Stack literacy = design leverage. Knowing that "this is an Astro content site" vs "a SvelteKit app" tells you the interaction budget and where a design will or won't survive. The map above is your triage tool too.
For the AI-first builder

R Choose stacks your agents drive and you own

  • Optimize for AI-drivability. You'll never touch the code, so the best stack is the one an agent generates and modifies most reliably — conventional framework + Tailwind + a component library. That's why the upper-right of the map matters more to you than to a hand-coder.
  • Good design should be a default, not a project. Picking DaisyUI or shadcn/ui means "looks designed" is the starting point, and your designer refines from there instead of rescuing it.
  • Own the deploy where it counts. You're already doing this (CDK static, Fly containers). Keep AWS serverless for the RAG/LLM backends you've invested in; front them with whatever fits. Evaluate Cloudflare/Railway before defaulting to Vercel on cost.
  • Consolidate so agents get fluent. Every distinct stack is a separate world your agents (and your designer) must re-learn. A small, deliberate set compounds: better prompts, reusable skills, shared components.
  • The designer is your highest-leverage collaborator now, not a handoff. With code-resident design systems, their tokens and component specs flow straight into what your agents build. Set that pipeline up once.
05 · The concrete move

A deliberate stack set for this repo

Not one stack for everything — a small, matched set, aligned with the direction already in your ai-coding-system-dev.md (off Webflow; evaluate DaisyUI/ShadCN; React/Svelte/Next; own a containerized deploy; steer clear of Vercel on cost). Triage each app by design ambition and interactivity, then use one of four lanes.

Lane 1 · Content & marketing

Astro + Tailwind + a few islands, deploy to S3/CloudFront (CDK) or Cloudflare Pages.

  • Fits: focusonfoundations.org, docs, demo hubs.
  • Move: add Tailwind + DaisyUI to the existing Astro site.

Lane 2 · Interactive products

SvelteKit or Next.js + Tailwind + shadcn/ui, TypeScript, deploy to a Fly/Railway container.

  • Fits: a real QRAG front end, future user-facing apps.
  • Move: pick one (SvelteKit = simpler; Next = biggest AI coverage).

Lane 3 · Internal tools & dashboards

FastAPI + Jinja/HTMX + Tailwind, deploy to Fly — the pattern you already run.

  • Fits: lesson-dash, prism-sync, admin panels.
  • Move: add Tailwind to lift the look with no new framework.

Lane 4 · Kids' apps & 3D

Vanilla + Three.js, static hosting. Keep it simple where design ambition is low or canvas-driven.

  • Fits: math-quiz, games, family apps.
  • Move: leave as-is; optionally share a tiny token file.

The sequence

1
Establish a code-resident design system once.

A Tailwind config (color/type/spacing tokens) + a component choice (DaisyUI for speed, shadcn/ui for control). The designer defines the tokens; it becomes the shared source of truth every lane and every agent reads. D this is your deliverable. R this is the one-time setup that makes all later UI good by default.

2
Finish the Astro site as the reference implementation.

Add Tailwind + the component system to the focusonfoundations.org branch. It becomes the template new content sites are cut from, and the proof of the owned-deploy pipeline (CDK).

3
Pick one app framework for Lane 2 and build one real app in it.

SvelteKit or Next — one, not both. A fresh QRAG front end is the natural candidate: it retires the Webflow dependency and proves the interactive-product lane end to end.

4
Retire Webflow deliberately, per app.

Once lanes 1 and 2 are proven, migrate the Webflow-fronted apps off it. No big-bang — one site at a time, onto the lane it belongs in.
