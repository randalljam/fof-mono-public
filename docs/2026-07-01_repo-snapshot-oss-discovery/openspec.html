Deep dive · spec-driven development

OpenSpec

An MIT, in-repo, markdown spec-driven-development system: it adds a lightweight spec layer so you agree on what to build before any code is written, instead of requirements living only in chat history. Its signature idea is delta specs — a change proposes ADDED / MODIFIED / REMOVED sections that merge into a central spec store when archived, giving you a durable, reviewable, versioned record of how each app behaves. Brownfield-first, context-light, and tool-agnostic (Claude Code, Cursor, Codex, and 30+ others).

The one-paragraph fit for you

You already keep intent in markdown — your plans/ folder, your dated doc-header convention, PROJECTS.md. OpenSpec is the formalized, agent-legible version of that habit: it turns ad-hoc plan docs into a structured propose → apply → archive lifecycle with an audit trail, and keeps a living spec of each app's current behavior that agents read before changing it. Its brownfield-first delta model suits your mature monorepo (change the diff, not the whole spec), and it works across your cloud Claude Code and local Codex lanes with no MCP or API keys.

✅ Why it fits

  • Persists intent as reviewable, versioned artifacts — not lost chat.
  • Delta specs keep context small (matters for cost + Fable's long runs).
  • Brownfield-first: treats existing code as the baseline.
  • Per-app specs map onto your plans/ + PROJECTS.md.

⚠️ What to weigh

  • Adds a directory + lifecycle discipline your collaborators must learn.
  • Overlaps your existing plans/ convention — decide coexist vs. migrate.
  • Young; the "Stores" cross-repo feature is beta.
01 · Technical

How it works

Folder structure (openspec init)

  • openspec/specs/ — the source of truth for how the system currently behaves, by domain (auth/, payments/…); requirements paired with Given/When/Then scenarios.
  • openspec/changes/ — one folder per proposed change.
  • openspec/changes/archive/ — completed changes, date-prefixed for a chronological audit trail.

A change's artifacts

proposal.md→delta specs (ADDED/MODIFIED/REMOVED)→design.md→tasks.md

The delta spec is the signature move: a change never edits the main specs directly — it proposes deltas that merge into openspec/specs/ on archive. That's the brownfield mechanism: it shows only what changes, avoids conflicts when multiple changes touch one spec, and keeps the LLM's context small. Artifact dependencies follow a configurable schema (a DAG) — default proposal → specs/design → tasks — and "progressive rigor": short lite specs for small work, full specs with scenarios for API/contract/migration/security changes.

The workflow (slash commands)

/opsx:explore→/opsx:propose→/opsx:apply→verify→/opsx:archive

Explore is a no-stakes thinking partner that reads your code and shapes a plan; propose creates the change folder; apply works through tasks.md; archive merges the deltas into the spec store and moves the change to the dated archive. Install: npm install -g @fission-ai/openspec@latest then openspec init. Integrates via per-tool Skills (.claude/skills/, .cursor/skills/) and command files — no MCP, no API keys. Stores (beta) enable planning in a repo of its own for cross-app/shared requirements.

vs. Spec Kit and vs. plan mode

vs. GitHub Spec Kit: Spec Kit is greenfield-oriented with a fixed pipeline and heavier per-feature files (a "senior architect in a box"); OpenSpec is brownfield-oriented, uses a central spec store + delta specs, and is context-light. vs. plain plan mode: plan mode is ephemeral (lost after the session); OpenSpec persists intent as reviewable, versioned, archived artifacts — durability and audit that plan mode doesn't give you.

Where it earns its place

OpenSpec's real gift to you is durability and reviewability of intent — turning "the plan lived in a Claude Code session and is now gone" into "the plan is a versioned artifact in the repo that the next agent (or EA) can read." That directly serves your human-out-of-the-loop goal: if you're not reading code, the spec is what you review and approve. It also pairs naturally with Superpowers (which governs how the agent works) — OpenSpec governs what gets built.

03 · Honest

Frictions

Overlap with plans/

You already have a plan-doc convention. Two systems for "intent" is confusing. Handle: decide whether OpenSpec replaces ad-hoc plan docs for feature changes (recommended for real features) while plans/ keeps meta/roadmap docs — one home per purpose.

Ceremony for small work

A full propose→apply→archive cycle is overkill for a typo fix. Handle: use lite specs (short, behavior-first) for small changes; reserve full specs for API/contract/migration/security work. Progressive rigor is built in.

Collaborator learning curve

EA and future agents must learn the lifecycle and slash commands. Handle: the commands are simple and in-repo; document the flow in AGENTS.md once, as you did for worktrees.

04 · Do this

How to trial it

1
Init on one app, on a branch.

openspec init in a worktree for a single app (say math-quiz), so nothing else is disturbed.

2
Run one real change end to end.

Take a small feature, go /opsx:explore → propose → apply → archive, and read what the archived spec + audit trail look like.

3
Compare to your current plan-doc flow.

Ask: did the persistent spec make the change easier to review without reading code? If yes, it's earning the ceremony; adopt it for feature work and write the convention into AGENTS.md.

Bottom line: OpenSpec is the natural upgrade to your markdown-plan habit — it makes intent durable, reviewable, and agent-legible, which is exactly what "Randy approves the spec, not the code" needs. Trial it on one app; keep plans/ for roadmap/meta and let OpenSpec own per-app feature intent. It pairs cleanly with Superpowers.
