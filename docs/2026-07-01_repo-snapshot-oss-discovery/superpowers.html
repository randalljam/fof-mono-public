Deep dive · skills + methodology

Superpowers

Jesse Vincent's (obra) MIT skills framework and software-development methodology: a folder of Markdown skills — built on Anthropic's SKILL.md standard — that auto-trigger to enforce a disciplined sequence: brainstorm → plan → verify-first (TDD) → implement → review, with a hard gate that the agent must earn the right to write code. It auto-creates a git worktree per task, and as of v6 it's vendor-neutral (Claude Code, Codex, Cursor, Pi, and more). It hit #1 on GitHub Trending.

The one-paragraph fit for you

This is the uncanny-alignment pick. Superpowers' using-git-worktrees skill does almost exactly what your worktree_bootstrap.sh does — default .worktrees/, verify-git-ignored-before-creating, auto stack setup, a clean test baseline per task. Its SKILL.md model is your "one source of truth, many platform wrappers" convention. Its planning gate is your convergence-planning discipline, enforced. In other words: it's a battle-tested, packaged version of the exact workflow you've been hand-building — worth mining even if you don't adopt it whole.

✅ Why it's a standout for you

  • Native worktree-per-task that mirrors your bootstrap conventions.
  • Skills as SKILL.md — same standard your skills/ targets.
  • Hard planning gate = your "plan before code" made enforceable.
  • Vendor-neutral: runs on Claude Code and Codex.

⚠️ What to weigh

  • Its .worktrees/ vs your Documents/Code/ + Codex worktrees = a 3rd scheme.

01 · Technical

How it works

Skills & install

Skills are Markdown files following Anthropic's Agent Skills convention — one folder per skill, skills/<name>/SKILL.md — distributed as a plugin (Claude Code: /plugin install superpowers@claude-plugins-official; Cursor, Codex, Copilot CLI, Gemini CLI, Kimi, Pi, OpenCode, Antigravity, Factory Droid also supported). A bootstrap skill, using-superpowers, is what makes the agent actually reach for the others. writing-skills is the meta-skill for authoring more.

The methodology (auto-triggered)

brainstorm (gate)→writing-plans→TDD→execute→subagent review
  • Planning gate ("earn the right to write code"): the brainstorming skill blocks code until a design is approved — explore context → ask clarifying questions one at a time → propose 2–3 approaches with trade-offs → present the design in sections, approval after each → write a dated design doc to docs/superpowers/specs/YYYY-MM-DD-<name>-design.md and commit it → hand off to writing-plans, which breaks work into 2–5-minute tasks with exact paths and verification steps.
  • Verify-first: test-driven-development enforces RED-GREEN-REFACTOR and will delete code written before its tests; verification-before-completion gates "done."
  • Subagent-driven development: a fresh subagent per task, two-stage review (spec compliance, then code quality) designed to be "cheaper, stricter, harder to game"; agents can run autonomously for hours on plan.
  • Durable memory: the committed dated design docs, plus a progress ledger so a controller that loses context can resume instead of redoing finished work.

Worktree-per-task, in detail

  • Step 0 detection: compares git rev-parse --git-dir vs --git-common-dir; if they differ (already in a worktree), it skips creation — "already in isolated workspace."
  • Native-first: prefers the harness's own worktree tooling (e.g. an EnterWorktree tool) before manual git.
  • Git fallback + safety: default location .worktrees/ at project root; verifies it's git-ignored (git check-ignore), adds to .gitignore and commits first if not; git worktree add "$path" -b "$BRANCH".
  • Setup + baseline: auto-detects the stack and runs install (npm/pip/cargo/go), then runs the test suite to confirm a clean start before work begins.

The move: harvest, don't wholesale-swap

Because your worktree conventions are deliberate (shared venv via _LOCAL_FILES, publish-to-origin bootstrap, Cursor windows), you probably don't want to switch to Superpowers' in-repo .worktrees/ scheme. But its planning gate, its TDD/verification skills, and its subagent-review structure are exactly the disciplines your operating contract asks for informally. The highest-value adoption is to port those specific skills into your own skills/ (with your provenance headers), keeping your worktree setup. It's the single best library to mine because it's the closest to what you already do.

03 · Honest

Frictions

A third worktree scheme

Its .worktrees/-in-repo default competes with your sibling-folder + Codex worktree conventions. Handle: disable/ignore its worktree skill (it detects an existing worktree and skips), or keep Superpowers only for its non-worktree skills. Don't run two worktree managers on one branch.

Prescriptive vs. Fable 5

Heavy, step-enforced methodology. Fable 5 guidance says over-prescriptive prompts reduce its quality. Handle: use the full gate on Claude Code/Opus; give Fable the goal and let it self-organize.

Skill-system stacking

Superpowers + compound-engineering + your skills/ = three overlapping systems. Handle: one canonical home (yours); harvest the best skills from each rather than running all three live.

04 · Do this

How to adopt

1
Install and run one gated cycle on a non-prod feature.

In a Claude Code session on math-quiz, install Superpowers and let brainstorming → writing-plans → TDD run once. Feel the planning gate and the TDD discipline first-hand.

2
Compare its worktree skill to your bootstrap.

See how using-git-worktrees handles detection, ignore-safety, and baseline tests. Decide whether any of it improves worktree_bootstrap.sh — then keep your scheme.

3
Port the planning gate + TDD skills into skills/.

Copy the ideas (not necessarily the files) into your own skills with provenance headers, so your one canonical skills system gains the enforced brainstorm-and-verify discipline without adopting a competing framework.

Bottom line: Superpowers is the closest existing library to the workflow you invented — which makes it the best one to mine. Harvest its planning gate, TDD, and subagent-review skills into your own skills/; keep your deliberate worktree/venv setup; and don't stack it live alongside compound-engineering and your own skills. Pairs naturally with OpenSpec (it governs how; OpenSpec governs what).
