01 · What Jason's template is

A personal Codex vault, not an app monorepo

The template is deliberately small. It gives Codex a stable place to look before acting and a stable place to write approved memory afterward.

TEMPLATE Root layout

  • projects/ for long-lived work.
  • experiments/ for short spikes.
  • people/ for collaborators and agents.
  • .codex/skills/ for repo-local procedures.
  • templates/ for repeatable project notes.

TEMPLATE Operating posture

The root AGENTS.md tells assistants to read project context, keep durable state on disk, update canonical files after approval, ask before side effects, and prefer concrete work over abstract planning.

Best use: personal assistant memory, project tracking, people context, recurring monitors, and writing-style capture.

The most valuable idea

It treats the repo itself as shared memory. The onboarding skill says to scan connected tools, propose durable notes, ask approval, and write those notes into the vault. That is the same design philosophy as your skills and plans, but it is more explicit about people, check-ins, and assistant-style life/work operations.

02 · What your repo has become

An apps-centric monorepo with agent infrastructure bolted into the beams

Your repo is not just a vault. It is a working portfolio: apps, shared Python, deployed surfaces, data rules, AI harnesses, branch ledgers, reusable skills, and now formal behavior specs.

FOF Applications

The repo is organized under apps/, with shared code in core/. It contains real app surfaces: QRAG, math quiz, Minecraft tooling, education lesson logger, voice/TTS, transcription, autolearner, and more.

FOF Skills

Shared skills live in skills/, with provenance headers and platform wrappers in places like agents/hermes/skills/. They encode procedures agents can run again later.

FOF Branch discipline

AGENTS.md is much heavier than the template because your real risk is branch confusion across local/cloud agents, worktrees, PRs, and user-local Cursor state.

FOF Data boundaries

S3-backed bulk data, gitignored data/ directories, PII cautions, manifest rules, and Chalice mirror rules are domain-specific machinery the template does not need.

FOF OpenSpec

The new OpenSpec layer gives opted-in apps living behavior specs and archived change intent. Autolearner is the trial app; holodeck, math-quiz, and other branches now have baseline stores.

FOF Holodeck

Holodeck aggregates worktrees, branches, apps, core modules, skills, OpenSpec stores, sessions, and deploy surfaces into a local dashboard. This is a control plane, not just memory.

04 · New OpenSpec work

OpenSpec is the missing behavior-contract layer

The template has project packets and goals. OpenSpec adds something stricter: current behavior specs, proposed delta specs, validation, task progress, and archived intent.

explore→ propose→ apply→ sync / verify→ archive

Repo-authored skills 5

opsx-explore, opsx-propose, opsx-apply, opsx-archive, and the new opsx-bootstrap composite for baselining existing apps.

Workflow-first specs

Autolearner's baseline spec starts with user workflows, then maps those workflows to requirements. This makes specs readable to Randy before they become machine-checkable artifacts.

Staged adoption

The OpenSpec guide splits app life stage (s0-experiment through s3-real) from spec machinery (readme-only through openspec-strict). That prevents ceremony from swallowing early experiments.

Roadmap companion

ROADMAP.md holds intended-but-unbuilt behavior. OpenSpec holds current behavior and proposed changes. That separation is cleaner than the template's general project README alone.

The core upgrade over the template

The template can remember that a project exists and what the goal is. OpenSpec can tell an agent what the app currently promises, what is being changed, which tasks are done, and when that change became the new baseline.

That is the natural next layer for a pure-AI-coder workflow.

06 · Pattern catalog

What to steal, what to skip

Filter these patterns by action. "Borrow" means adapt into your system. "Keep yours" means your existing approach is stronger. "Skip" means the template is solving a smaller problem.

BORROW Assistant onboarding

The template's onboarding skill is more explicit about first-run assistant setup: scan context, ask focused questions, identify plugin gaps, propose monitors, and write memory only after approval.

Adapt as: a Randy onboarding / session-start skill that can populate holodeck registry gaps and people/project notes.

BORROW people/ notes

Your repo knows apps and agents better than people. A light people/ layer could capture collaborators, family users, EA workflows, and communication preferences without polluting app docs.

BORROW GOAL.md / RESULT.md

For long-running projects, these are cleaner than chat memory. They pair well with your existing mission-closeout skill and OpenSpec archives.

BORROW Write-like-me bootstrap

This is not core engineering, but it fits your Hermes/EA direction: create a reusable writing posture from approved authored messages, with strict approval gates.

KEEP YOURS Skill architecture

Your skills/ source-of-truth model, provenance headers, and platform wrappers are more mature than a Codex-only .codex/skills/ folder.

KEEP YOURS Branch safety rules

The template's safety rules are right for a vault. Your branch/worktree/cloud-agent hazards require the heavier rules in AGENTS.md.

KEEP YOURS OpenSpec layer

The template's project docs do not replace specs. OpenSpec is now your route to "approve the spec, not the code."

KEEP YOURS Holodeck control plane

This is the part the template does not attempt: live cross-worktree inventory with apps, specs, skills, sessions, and deploy surfaces.

SKIP Re-rooting around projects/

Your app-centric monorepo convention is already settled. Adding projects/ as the primary root would fight apps/, core/, and deployment reality.

SKIP Codex-only skill placement

The template assumes Codex is the main consumer. Your system uses Cursor, Claude Code, Codex, Hermes, and future wrappers, so procedures should stay platform-agnostic first.

WATCH Recurring monitors

The template's 9 AM / 4 PM check-ins are useful, but your better implementation target is holodeck: recurring collector refresh, app/status digest, and branch-risk summary.

WATCH Simple HTML artifacts

The template has a skill for information-first HTML artifacts. Your repo snapshot style already proves the pattern; formalizing a local version would make future reports easier.

07 · Practical recommendation

Adopt the vault ideas as a thin layer, not a new architecture

The right synthesis is additive: keep apps, skills, OpenSpec, and holodeck as the core. Add selected personal-vault files only where they improve human/assistant memory.

Decision picker: where should a piece of context live?

Put it in OpenSpec.
Current behavior belongs in apps/<app>/openspec/specs/. If the behavior is changing, create a delta under changes/<change>/, then archive it when complete.

Recommended sequence

1
Keep the existing monorepo architecture.

Do not move app work into a template-style projects/ root. The app-centric structure and shared core/ layer are still right.

2
Mine the template skills.

Port the useful ideas - onboarding, simple HTML artifacts, write-like-me, goal/result closeout - into skills/ using your provenance/header conventions.

3
Let OpenSpec and ROADMAP split present vs future.

Current behavior goes into living specs. Aspirations, voice-memo ideas, and Now/Next/Later stay in app roadmaps until they become an opsx-propose change.

4
Promote holodeck to the home screen.

It should show branch/worktree risk, app stage, spec stage, active changes, recent sessions, deploy surfaces, and missing registry metadata.

5
Add a light personal-memory lane only when needed.

If people notes and assistant check-ins become useful, add them as a separate memory layer and have holodeck index them. Do not let them blur app specs or engineering docs.
