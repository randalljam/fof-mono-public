Compare & contrast · knowledge-graph architecture

Marble's os-taxonomy vs the Deutsch Graph

Marble (a kids-learning startup) just open-sourced the Marble Skill Taxonomy: 1,590 "micro-topics" of primary-school learning wired into a 3,221-edge prerequisite DAG, aligned to 7 national curricula. The headline finding: they used no graph library, no graph database, and no framework at all — the repo is four plain JSON files, four JSON Schemas, and one dependency-free validator. Their architecture and ours converge on the same core philosophy (plain-text property graph + integrity validator + checksum manifest), and differ exactly where our purposes differ: theirs is a published dataset exported from a private product database; ours is a self-contained factory that compiles a private corpus into a graph, with the build code, curation overlays, and viewer all in the repo.

The one-paragraph verdict

Nothing in os-taxonomy says "we chose the wrong architecture" — it says the opposite: an independent, well-funded team shipping a serious knowledge graph landed on the same no-database, plain-JSON, validator-enforced pattern we chose in architecture.md D1. What they do better is publication engineering: formal JSON Schemas, per-file output checksums, semver + CHANGELOG, a genuinely sophisticated license split (ODbL database / CC BY-SA content / codes-only for encumbered sources), and richer edge metadata (every prerequisite edge carries a hard/soft strength and a one-line human reason). Those are the four things worth adopting — two now, two when the Deutsch Graph goes public.

✅ Where they're ahead

  • Edge reason + strength on every dependency — curation you can review.
  • Formal JSON Schema per file (additionalProperties:false).
  • Output checksums + counts in manifest.json.
  • Publication kit: ODbL/CC split, PROVENANCE.md, CITATION.cff, CHANGELOG, semver.
  • Per-node evidence[] + assessmentPrompt — mastery checks baked into the node.

✅ Where we're ahead

  • The whole factory ships: build pipeline, curation overlays, input pinning — theirs is an export of a private Postgres DB.
  • Multi-layer graph (8 node types, L0–L5 digestion ladder) vs one node type + one edge type.
  • Viewer in-repo (file://-capable, explore/research modes) — theirs is closed, hosted only.
  • Media traversal: every QA node jumps to the YouTube moment; excerpts resolve to chapter/interview.
  • Input provenance: build pins every source file by sha256.

The pipeline (what ships vs what doesn't)

private Postgres DB→exportTaxonomy.mjs (not shipped)→repo: 4 JSON + schemas + validator→consumers load JSON directly
same DB→hosted 3D viz at withmarble.com/curriculum (closed source)
  • No graph library, no runtime: the README is explicit — "Pure data — no runtime, no dependencies. Load the JSON and go." package.json has zero dependencies; the only script is the validator. Consumers get a 5-line snippet building a Map by id.
  • Node model: one type (mt_… micro-topic) with a controlled type enum (CONCEPTUAL / PROCEDURAL / REPRESENTATIONAL / LANGUAGE / META), subject/domain, age range, precomputed centrality, evidence[] mastery criteria, an assessmentPrompt (with a {{name}} child-name placeholder), and standards[] cross-refs.
  • Edge model: one type — {topicId, prerequisiteId, strength: hard|soft, reason}. Directed, acyclic by intent. Every edge explains itself in one line: "Must understand vibrations make sound before finding volume patterns."
  • Rollups: 183 hand-written clusters (one parent-friendly paragraph per subject × domain × age band) — human-authored community summaries, GraphRAG-style but curated.
  • Validator (validate.mjs, node stdlib only): declared counts vs reality, id format, duplicate detection, referential integrity for both edge endpoints and topic→standard refs, a "codes-only" licensing invariant, and sha256 checksums of every data file against manifest.json. (Notably absent: an acyclicity check on the DAG — enforced upstream, trusted in the export.)
  • Licensing machinery: ODbL 1.0 for the database, CC BY-SA 4.0 for Marble-authored text, and per-source upstream licenses for standards. Encumbered sources (NGSS, C3, IB) ship codes only — the identifier and the link survive, the verbatim text is omitted, and the validator enforces that nothing leaks.

03 · The interesting differences

Five deep contrasts

1 · Export artifact vs self-contained factory

Marble's source of truth is a private Postgres database; the repo is a snapshot produced by an export tool they didn't publish, and community contributions can't rebuild it. Our source of truth is the corpus + committed overlays, and the repo carries everything needed to regenerate the graph from scratch (fetch → build → validate). For a product company protecting a moat, their split is rational. For a solo-dev, git-first, agent-operated workflow, ours is — an agent can rebuild, extend, and verify the whole thing in one session, which is exactly what has happened three times so far.

2 · One deep relation vs many layered ones

Their entire graph is engineered around a single query: "what must a learner master before X?" — one node type, one edge type, DAG semantics, precomputed centrality. Ours is engineered around traversal between layers: category → claim → verbatim excerpt → the exact minute of the interview. Neither generalizes to the other's job. The lesson worth taking: their single relation is semantically strong (direction, strength, reason), while our bridges are structurally typed but semantically silent. When claim→claim or concept→concept relations arrive (roadmap R4), they should be born with direction + type + reason, prerequisite-style — the Deutsch corpus genuinely has this structure ("you need explanation before good explanation before hard to vary").

3 · Opaque ids vs semantic slugs

Their mt_N8CpN1EJrP ids never break on rename and never collide — but a diff or a validator error is unreadable without a lookup, fine when no human reviews data diffs. Our work:2018-12-08_joe-boswell-constructor-theory ids make every diff, error, and URL self-describing — at the price of the rename problem, which the alias overlay handles (and which the Deutsch Well import exercised for real: 4 aliases fixed 35 dangling references). Given that PR review of data changes is a core requirement here (AGENTS.md posture), semantic slugs remain the right call.

4 · They checksum outputs; we checksum inputs

Their manifest answers a consumer's question: "is the file I downloaded the file they published?" Ours answers a maker's question: "exactly which corpus state produced this graph?" These aren't alternatives — a dataset intended for others needs both, and adding per-file output sha256 to build-manifest.json is a ~10-line change.

5 · The codes-only pattern is our D3 rule, weaponized for licensing

Their cleverest move: for standards they can't relicense (NGSS, IB, C3), they ship the identifier and the relationship but not the text — and the validator enforces the redaction. That is structurally identical to our D3 pointer-not-text rule (graph stores question text and pointers; verbatim answers stay in the corpus). When the Deutsch Graph goes public, the same mechanism handles the copyright question you deferred: publish structure, topics, claims, and pointers; gate verbatim excerpt/answer text per-source with a textIncluded-style flag, validator-enforced. Their PROVENANCE.md is the document to copy the shape of.

04 · Actionable

What to adopt, in priority order

now · cheap
Edge reason on curated edges.

Add an optional reason field to overlays/category_topics.jsonl entries and carry it onto category_topic edges (viewer tooltip + panel). Make it mandatory for future claim/concept relations. This is the single best idea in their repo.

now · cheap
Output checksums in build-manifest.json.

Alongside input pinning, record bytes + sha256 for every file under graph/. Distribution integrity for free, and stale-artifact detection (did someone hand-edit an output?).

soon
Per-claim evidence[] / understanding prompts.

Their assessmentPrompt ("can {{name}} explain why…") is exactly the Worldview Mirror mechanic: a per-claim "do you actually hold / understand this idea?" probe. Author these as an overlay on the 127 Well claims — it converts the graph from reference material into an interactive instrument.

soon
Precomputed centrality.

They ship a centrality score per node; we size viewer nodes by raw counts. A degree/PageRank-style score over the full edge set (computed at build, stored on topic/category/work nodes) would make explore-mode sizing and "what matters most" ordering principled.

at publish
The publication kit.

Formal JSON Schemas for each node/edge file, envelope counts, semver + CHANGELOG.md, CITATION.cff, PROVENANCE.md with per-source terms, and codes-only-style textIncluded flags for rights-encumbered verbatim text. Wholesale, this is the template for "Deutsch Well 2.0 goes public."

What not to adopt

  • The private-DB + export split. It would break the agent-rebuildable, PR-reviewable loop that the whole app is designed around.
  • Opaque ids. Wrong tradeoff for a repo where humans and agents review data diffs (contrast #3).
  • Monolithic data files. A single 1.7 MB topics.json would collide with the 512 KB pre-commit hook and produce unreviewable diffs; sharded JSONL stays.
  • A graph database. The strongest external signal yet for architecture.md D1: at 10³–10⁴ nodes, nobody needs one — not them at 1.6k nodes, not us at 5.7k.
05 · Confirmation

What this validates about the Deutsch Graph

  • Plain files + validator beats infrastructure at this scale — independently chosen by both projects (their README even brags about it).
  • Exclude embeddings, keep cross-refs — identical decision, identical reasoning ("derived / recomputable").
  • Human rollups over clusters — their 183 hand-written cluster summaries are the same layer as our category definitions + chapter summaries: curated digest text stored on rollup nodes, not LLM-generated at read time.
  • Checksum-manifest provenance — both treat "which bytes, exactly?" as a first-class artifact.
  • Redaction as architecture — their codes-only licensing pattern and our pointer-not-text rule are the same idea; ours is already positioned for the eventual public release.

Bottom line

os-taxonomy is a dataset with excellent publication engineering; the Deutsch Graph is a knowledge factory with excellent build engineering. The architectures agree on every load-bearing choice (no DB, plain-text property graph, integrity validator, checksums, no embeddings). Adopt their edge-reasons and output-checksums now, their assessment-prompt idea for the Worldview Mirror soon, and their license/provenance kit whenever the graph goes public.
