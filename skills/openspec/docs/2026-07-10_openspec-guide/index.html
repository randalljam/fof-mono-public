OpenSpec · spec-driven development, sized to fit

The spec system, and how to actually use it here

OpenSpec is an MIT, in-repo, markdown spec system: agree on what to build before code is written, and keep a living spec of what each app does. This page explains the whole machine — then answers the real question: it feels heavy for ~20 pre-production apps built by one operator and his agents. What's the right-sized version? Section 06 is the proposal; section 07 is the honest alternative.

The one-paragraph verdict

Don't adopt OpenSpec wholesale, and don't drop it. Its full ceremony is designed for production apps and multi-engineer teams — but your actual failure mode (specs untracked, PROJECTS.md stale within a month) is exactly what its living-spec + archive machinery fixes. The move is a staged ladder: no specs for sketches, one workflow-first spec file + a roadmap companion for apps in active development, and the full delta-spec change control only where an app has earned it (deployed, real users). OpenSpec's own primitives support every rung — verified against the CLI on 2026-07-10.

01 · Orientation

The mental model

OpenSpec is two halves that meet in one folder. Neither half picks the AI model — your chat session does; OpenSpec just tells that model what procedure to follow.

CLI The terminal half

openspec init / list / status / validate / archive — file structure, validation, and the delta-merge. Deterministic, no LLM, no API keys. Installed globally: @fission-ai/openspec@1.5.0.

AI The agent half

/opsx:explore, /opsx:propose, … — workflow instructions your AI assistant follows in Cursor / Claude Code / Codex. This repo authors them as skills in skills/openspec/ instead of generated wrappers (--tools none).

One store per opted-in app

apps/<app>/openspec/
  config.yaml                      ← schema + project context + artifact rules (agent guidance)
  specs/<capability>/spec.md       ← living spec: current behavior (source of truth)
  changes/<change>/                ← one folder per proposed change (the delta)
  changes/archive/YYYY-MM-DD-<change>/   ← completed changes: the audit trail

The signature move is the delta spec: a change never edits specs/ directly. It proposes ADDED / MODIFIED / REMOVED requirements that merge into the living spec on archive. Brownfield-first, small context, reviewable diffs of intent.

Terminology — don't mix these

TermWhat it isExample
Workflow IDInternal selector used by profiles/config to decide which actions get installedpropose, explore, verify
CommandUser-facing action typed in an AI chat/opsx:propose
SkillInstruction file teaching an assistant how to perform a commandskills/openspec/opsx-propose/README.md
CLI commandTerminal command; inspects, validates, scaffolds, mergesopenspec validate --all
Capability (domain)A spec folder inside one app — a behavior area, not an internet domain and not an appspecs/app/, specs/auth/

Capability granularity, settled: one app can have many spec files (auth/, billing/, search/) — but it doesn't have to. For an early app, one broad capability named app is fully supported and validated. Split only when the file gets too big or areas change independently. Autolearner's baseline uses exactly this: specs/app/spec.md.

02 · The loop

Lifecycle & workflows

The core loop, with the two optional detours. Expanded workflow IDs (section 03) add finer-grained control points to the same loop — they are not extra phases.

explore→ propose→ apply→ sync / verify→ archive

explore optional

No-stakes thinking partner. Reads code + existing specs, compares options, clarifies requirements. Creates no artifacts.

propose

Creates changes/<name>/ with all planning artifacts in one pass: proposal, delta specs, design (when needed), tasks. Progressive rigor: lite for small work, full Given/When/Then for contracts, migrations, security.

apply

Implements tasks.md, checking off items as code lands. The change folder is the working memory between sessions and agents.

sync optional

Merges delta specs into the living store before archive — mainly for parallel changes that need the baseline updated early.

verify expanded

Checks the implementation against the artifacts — completeness, correctness, coherence — before closeout.

archive

Finalizes: merges deltas into specs/, moves the change to changes/archive/YYYY-MM-DD-<name>/. The living spec is now current behavior; the archive is the audit trail.

Which action, when

SituationUse
Requirements fuzzy, options need comparison, codebase needs investigationexplore
Scope clear, one quick planning passpropose
Want to review each planning artifact before the next is writtennew + continue
Explicit scaffold first, then all artifacts at oncenew + ff
Planning done; write the codeapply
Parallel changes need the living spec updated before archivesync
Implementation done; check it against the artifactsverify
One finished change becomes current behaviorarchive
Several finished changes at oncebulk-archive
Onboard an existing un-specced app into OpenSpecbootstrap repo skill
Guided first-time walkthrough on real codeonboard

04 · The paper trail

Artifacts

Seven artifact types across two areas: the living store, and per-change folders. Every one is plain markdown (plus one YAML).

Anatomy of a living spec — and its readability problem

Stock format

## Purpose
Two–four sentences.

## Requirements
### Requirement: Mastery Scheduling
The system SHALL ...
#### Scenario: Later rounds target
####   unmastered concepts
- **WHEN** ... - **THEN** ...

Requirements + Given/When/Then scenarios. Precise, testable, agent-legible — but a flat requirements list reads like a wall: folding autolearner's 11 requirements tells you almost nothing about what the app does or which journey each requirement serves.

Workflow-first format PROPOSED

## Purpose
## Workflows                ← new
### Workflow: Student
###   practices a concept
Open → exercise → think-aloud
→ assessment → repeat.
Exercises requirements:
Mastery Scheduling, Attempt
Submission, Think-Aloud
Assessment ...

## Requirements   (unchanged)

A ## Workflows section on top: each user journey as a one-line narrative, naming the requirements it exercises. Fold to Workflows → you see what the app does. Verified 2026-07-10: openspec validate --all --strict passes with the extra section. No fork, no custom schema.

What spec.md is not for (settled in the Cursor thread): roadmap, vision, and intended-but-unbuilt behavior don't belong in the living spec — it's a behavior contract. Intended changes live in delta specs; vision/roadmap live in a companion doc (section 06) or plans/. Keeping the contract strict is what keeps validation and archive-merging reliable.

06 · The key deliverable

How do I apply this ★

The honest fit assessment, then the adapted proposal: Staged OpenSpec — five moves that keep OpenSpec's machinery where it earns its ceremony and stay out of the way everywhere else.

The fit, honestly

Why full OpenSpec is too heavy right now

  • ~20 apps, most pre-deployment, built rapidly in parallel — full propose→apply→archive per change is ceremony the work hasn't earned.
  • Solo operator + agents, not a multi-engineer team needing granular change control.
  • Stock spec format is hard to read as "what does this app do" — the exact judgment you need to make ("am I happy? what next?").
  • No native home for roadmap/vision, your dominant mode of thinking about these apps.
  • Per-app stores have no composability — nothing shares stack/UI/deploy knowledge across apps (Stores, the cross-repo feature, is beta).

Why "just drop it" is wrong too

  • Your actual history: specs untracked, or written once and stale (PROJECTS.md doesn't know half the current apps). The living-spec + merge-on-archive loop is the only mechanism on the table that keeps specs current.
  • The end-state vision — "Randy approves the spec, not the code" — needs a durable, reviewable spec artifact. That's OpenSpec's whole product.
  • Validation, task-checkbox progress, and dated archives are free machine-readable signals — holodeck already consumes them.
  • QRAG is production-like today; more apps will get there. The heavy rung will be needed — just not everywhere at once.

Move 1 · Two axes + tags — app stage, spec stage, and everything else

Three different things were tangled in the first draft of this ladder; they come apart cleanly. App stage says where the app is in its life. Spec stage says how much spec machinery it carries. Tags hold everything cross-cutting (activity, users, money, minors…). All three are curated per app in holodeck's registry.yaml and shown on the dashboard. Promotion on either axis is deliberate — a small, reviewable event.

Axis 1 · App stage

StageMeaning
S0 · experimentSpike / swing-for-the-fences; may be abandoned
S1 · devReal app being built; not deployed (most apps today)
S2 · deployedLive somewhere with a dev + production path — the defining marker (lesson-dash, prism-sync, the FOF site; QRAG sits at this stage's upper end)
S3 · realReal users beyond yourself/household, real stakes — obligations, money, or minors at scale. Nothing is here yet.

Axis 2 · Spec stage

Spec stageMachinery
readme-onlyNo OpenSpec. README "What it does" (3 lines) + "Roadmap" section. Git is the change control.
openspec-single-specOne living spec (specs/app/, workflow-first) + ROADMAP.md, via opsx-bootstrap. Changes = lite propose, or spec-edit-with-commit for small shifts.
openspec-coreFull core loop per change: explore → propose → apply → archive. One or a few capabilities. This is where real change control switches on.
openspec-strictCapability-split specs, full-rigor deltas with scenarios, verify before archive (expanded profile). Nothing merges without a validated change.

Tags — the flexible third dimension iterate freely

Cross-cutting attributes don't belong in either stage — an app can be deployed and dormant, or in dev and destined for kid users. Keep them as tags in the registry, provisional by design: active-dev · dormant · done (deployed, simple, finished) · real-users · revenue · minors · education · internal · public-facing. The registry treats tags as free-form strings precisely so renaming, splitting, or redefining them is a one-line edit, never a schema change — expect this vocabulary to be iterated.

Typical mapping — S0→readme-only, S1→openspec-single-spec, S2→openspec-core, S3→openspec-strict — but the axes deliberately move independently: a deployed-and-done utility can stay at openspec-single-spec forever, and a dev app heading somewhere serious can adopt openspec-core early.

Suggested initial placements (to confirm): S2 · deployed QRAG (upper end), math-quiz, lesson-logger, prism-sync, FOF site · S1 · dev autolearner, holodeck, minecraft mods, content-studio, voice-router, stellar-transcriber, deutsch-graph · S0 · experiment family/games experiments and other fresh swings.

Move 2 · Workflow-first specs — fix the readability problem

Every living spec gets a ## Workflows section above ## Requirements: each user journey as a one-line narrative naming the requirements it exercises. Reading folded = what the app does; every requirement is reachable from a journey, so "is this doing what I want, and what do I expand next?" is answerable from the spec alone. Validator-verified (strict mode) — this is a house style encoded in config.yaml rules, not a fork. First act: reshape autolearner's baseline via a proper change (which also creates the missing audit trail).

Move 3 · Roadmap & vision companions — where "where I'm going" lives

apps/<app>/ROADMAP.md

Vision paragraph · Now / Next / Later · dated idea inbox. Deliberately outside the OpenSpec store: the spec stays a strict behavior contract, the roadmap holds everything aspirational. Cross-app/portfolio roadmap stays in plans/.

The graduation pipeline

voice memo → idea inbox → Now/Next/Later → opsx-propose → delta spec → living spec. SuperWhisper transcripts get captured (dated) and triaged into idea inboxes; ideas graduate upward; only when work is real does one become an OpenSpec change. Holodeck later grows a memo/roadmap collector — its registry and specs layers already prove the pattern.

Move 4 · Composable profiles — the hierarchical, reusable layer

The monorepo already layers context (repo AGENTS.md → app AGENTS.md/README → change). Extend that to specs with a shared profile library — specs-shared/ (or under skills/openspec/profiles/): stack lanes (the four from Web Stacks × Design), UI-template profiles, style guides, deployment guides. An app's config.yaml context and spec Purpose declare which profiles it inherits; agents state those inherited assumptions when they start work. An app spec then only records what's different — so comparing two apps is "same lane, these deltas," and progression toward deployment = swapping/adding profiles. When OpenSpec's cross-repo Stores feature matures, profiles can migrate into it; until then plain referenced markdown does the job.

Move 5 · Bootstrap + holodeck wiring

opsx-bootstrap SHIPPED TODAY

One pass per app: init store → explore → workflow-first baseline via a baseline-current-behavior change → ROADMAP.md scaffold → validate → archive → register stage. The repeatable version of what the Cursor agent did ad hoc for autolearner. skills/openspec/opsx-bootstrap/README.md.

Holodeck as the spec HQ

Add stage: to registry.yaml (S0–S3 chips on the dashboard); the existing specs layer already shows domains, change artifacts, and task progress. Later: roadmap counts and a voice-memo inbox as collectors. The control center becomes where you see the whole ladder at a glance.

07 · The other road

The alternative: SPEC.md + git, no OpenSpec

The credible non-OpenSpec paradigm isn't another framework — it's the pattern this repo already invented for prism-sync: one living SPEC.md per app, git as the only change control.

The shape

  • One apps/<app>/SPEC.md: what it is · workflows · current behavior (light requirements) · milestones (M1 ✓, M2, M3) · Now/Next/Later roadmap.
  • Machine-readable header (stage, lane, status) that a holodeck collector reads — same dashboard, different source.
  • Change control = commits and PRs touching SPEC.md alongside code; review the SPEC.md diff instead of a proposal.
  • Same composable profiles layer (Move 4) — it's tool-agnostic markdown either way.

The trade

  • Pro: zero new tooling or lifecycle; one file per app; matches proven habits (prism-sync's SPEC.md, milestone plans); nothing to keep in sync.
  • Pro: roadmap and behavior live on one page — the readability you wanted, by default.
  • Con: no validation, no structured deltas, no dated change archive — history is commit-grained, and "what changed in intent" means archaeology in git log.
  • Con: parallel agents editing one SPEC.md collide; OpenSpec's change folders exist precisely to prevent that.
  • Con: no enforced separation of "current" vs "intended" — the drift that made past specs go stale.

The reconciliation — you don't actually have to choose

Look closely and the alternative is the readme-only / openspec-single-spec rungs with the OpenSpec folder shape removed. The staged proposal keeps those rungs almost exactly this light (one readable spec + roadmap, git-driven) while preserving a no-migration upgrade path: when an app earns openspec-core, its spec is already in the store format, and delta change control switches on without rewriting anything. Run the ladder; if after a few months the core/strict machinery still isn't earning its keep, collapsing back to plain SPEC.md files is a rename, not a rebuild. Worth a side-glance later: Agent OS's three-layer standards/product/specs model — but it's a heavier system, not a lighter one.

The through-line

The goal was never "have specs." It's "Randy approves the spec, not the code" — which requires specs that are readable (workflow-first), current (living store + archive), right-sized (the ladder), composable (profiles), fed by how you actually think (voice memos → roadmaps), and visible in one place (holodeck). Every move above serves that end-state; none blocks the others; and the exit — plain SPEC.md files — stays open the whole way.
