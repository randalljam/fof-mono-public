**OpenSpec** is an MIT, in-repo, markdown spec-driven-development system from [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec). It adds a lightweight spec layer so you agree on *what* to build before code is written. Its signature move is **delta specs** — a change proposes ADDED / MODIFIED / REMOVED sections that merge into a central spec store on archive, giving a durable, reviewable record of how each app behaves.

This folder holds **platform-agnostic skills** that wrap the real `@fission-ai/openspec` CLI and layer this repo's conventions on top. Tool-specific wrappers (`.claude/skills/`, `.cursor/skills/`) are deferred until the trial proves useful.

## Key decisions
- **Wrap the real CLI**, don't reimplement: skills drive `openspec init/validate/archive/status` and the `/opsx:*` slash-command intent, so we get OpenSpec's tooling, validation, and delta-merge for free.
- **Opt-in, not forced**: OpenSpec is trialed on selected apps only. `docs/` keeps roadmap/meta docs; OpenSpec owns per-app feature intent for opted-in apps. No repo-wide mandate.
- **Per-app location**: an opted-in app's store lives at `apps/<app>/openspec/`, created by `openspec init apps/<app>` from repo root.
- **Repo skills only for now**: no `.claude/skills/` or `.cursor/skills/` generation yet (use `openspec init --tools none`). Propagate to tool wrappers later if helpful.

## Terminology
- **Workflow ID**: the internal OpenSpec selector used by profiles and config (for example, `propose`, `explore`, `verify`). Workflow IDs decide which actions are installed when OpenSpec generates tool wrappers.
- **Command**: the user-facing action typed in an AI assistant chat (for example, `/opsx:propose` in Claude Code or `/opsx-propose` in Cursor-generated command integrations).
- **Skill**: the instruction file generated by OpenSpec or authored in this repo that teaches an assistant how to perform a command (for example, `openspec-propose` upstream or `skills/openspec/opsx-propose/README.md` here).
- **CLI command**: a terminal command such as `openspec validate`, `openspec status`, or `openspec archive`. CLI commands inspect, validate, scaffold, and move files; AI commands/skills do the planning and implementation work.

In short: profiles select **workflow IDs**; selected workflow IDs can generate **AI commands** and **skills**; terminal-only `openspec ...` commands are the CLI layer.


## Lifecycle
```text
explore  →  propose  →  apply  →  sync  →  archive
```
| Step | Skill | What happens |
|------|-------|--------------|
| Explore | [`opsx-explore/README.md`](opsx-explore/README.md) | No-stakes thinking; reads code + existing specs; no artifacts created |
| Propose | [`opsx-propose/README.md`](opsx-propose/README.md) | Creates `openspec/changes/<name>/` with proposal, delta specs, design, tasks |
| Apply | [`opsx-apply/README.md`](opsx-apply/README.md) | Implements `tasks.md`, checks off items, writes code |
| Sync | (core profile; no repo skill yet) | Merges delta specs into `openspec/specs/` while the change remains active |
| Archive | [`opsx-archive/README.md`](opsx-archive/README.md) | Syncs deltas into `openspec/specs/`, moves change to dated archive |

In Cursor, invoke skills by reading the README (e.g. "use opsx-propose"). Upstream slash commands are `/opsx:explore`, `/opsx:propose`, `/opsx:apply`, `/opsx:archive` (or `/opsx-explore` etc. in Cursor-native integrations).


## Core Profile
The installed OpenSpec CLI reports the `core` profile as these workflow IDs: `propose`, `explore`, `apply`, `sync`, `archive`. If tool wrappers are generated, those workflow IDs become these AI commands and skills:

| Workflow ID | AI command intent | Generated skill name | Purpose |
|-------------|-------------------|----------------------|---------|
| `explore` | `/opsx:explore` | `openspec-explore` | Think through ideas, investigate code, and clarify requirements before creating artifacts |
| `propose` | `/opsx:propose` | `openspec-propose` | Create a change and generate planning artifacts in one step |
| `apply` | `/opsx:apply` | `openspec-apply-change` | Implement the tasks from a change, updating task checkboxes as work completes |
| `sync` | `/opsx:sync` | `openspec-sync-specs` | Merge delta specs into the living `openspec/specs/` store without archiving the change |
| `archive` | `/opsx:archive` | `openspec-archive-change` | Finalize a completed change and move it to the dated archive |

This repo currently authors only four repo skills: `opsx-explore`, `opsx-propose`, `opsx-apply`, and `opsx-archive`. The `sync` action is available through the CLI/underlying OpenSpec workflow but does not yet have a dedicated repo skill.


## Expanded Commands
OpenSpec's expanded/custom profile can select additional workflow IDs. These are not separate "phases"; they are optional actions you can install when you want more control than the default quick path.

| Workflow ID | AI command intent | Generated skill name | Purpose |
|-------------|-------------------|----------------------|---------|
| `new` | `/opsx:new` | `openspec-new-change` | Create an empty change scaffold and wait before generating artifacts |
| `continue` | `/opsx:continue` | `openspec-continue-change` | Create the next missing artifact based on the schema dependency order |
| `ff` | `/opsx:ff` | `openspec-ff-change` | Fast-forward through all missing planning artifacts at once |
| `verify` | `/opsx:verify` | `openspec-verify-change` | Check implementation against artifacts for completeness, correctness, and coherence |
| `bulk-archive` | `/opsx:bulk-archive` | `openspec-bulk-archive-change` | Archive multiple completed changes, resolving spec conflicts against the implemented code |
| `onboard` | `/opsx:onboard` | `openspec-onboard` | Walk through a guided end-to-end OpenSpec tutorial on the real codebase |

Upstream docs also describe `/opsx:update` for revising an existing change's planning artifacts without editing code. In `@fission-ai/openspec@1.5.0`, `update` is documented but is not present in the installed `ALL_WORKFLOWS` list, so treat it as an upstream/newer-docs capability until verified in a newer CLI version.


## Which Action To Use
| Situation | Use |
|-----------|-----|
| Requirements are fuzzy, architectural options need comparison, or the codebase needs investigation | `explore` |
| Scope is clear and you want one quick planning pass | `propose` |
| You want to review each planning artifact before moving to the next | `new` + `continue` |
| You want an explicit scaffold but can generate all artifacts in one pass | `new` + `ff` |
| Planning is complete and code should be written from `tasks.md` | `apply` |
| Delta specs should update the living spec before archive, usually for parallel changes | `sync` |
| Implementation is complete and should be checked against the artifacts before closeout | `verify` |
| One completed change should become current behavior and move to archive | `archive` |
| Multiple completed changes need to be archived together | `bulk-archive` |
| A new user wants a guided OpenSpec walkthrough on real code | `onboard` |
| Existing artifacts need to be revised because the plan changed, but code should not be edited | `update` if available; otherwise manually edit artifacts with user approval |


## Artifacts
OpenSpec uses two artifact areas inside an opted-in app:

| Path | Artifact | Purpose |
|------|----------|---------|
| `apps/<app>/openspec/config.yaml` | Store config | Defines the schema plus project context and artifact-specific rules shown to agents |
| `apps/<app>/openspec/specs/<domain>/spec.md` | Living spec | Source of truth for current behavior after completed changes are synced/archived |
| `apps/<app>/openspec/changes/<change>/proposal.md` | Proposal | Explains why the change exists, what will change, impact, and non-goals |
| `apps/<app>/openspec/changes/<change>/specs/<domain>/spec.md` | Delta spec | Describes ADDED / MODIFIED / REMOVED requirements and scenarios for the change |
| `apps/<app>/openspec/changes/<change>/design.md` | Design | Captures technical approach, decisions, risks, alternatives, and test strategy when needed |
| `apps/<app>/openspec/changes/<change>/tasks.md` | Tasks | Implementation checklist that `apply` works through and checks off |
| `apps/<app>/openspec/changes/archive/YYYY-MM-DD-<change>/` | Archived change | Preserves the completed proposal, design, tasks, and delta specs for audit history |

Delta specs are written under a change first. On `sync` or `archive`, OpenSpec merges those deltas into `openspec/specs/`, which becomes the current behavior baseline for future work.


## Opt in an app
From the repo root, on a feature branch for that app:
```bash
openspec init apps/<app> --tools none --profile core
```
Creates:
```text
apps/<app>/openspec/
  config.yaml
  specs/              # source of truth for current behavior
  changes/            # one folder per proposed change
  changes/archive/    # completed changes (date-prefixed)
```
The `core` profile provides `explore`, `propose`, `apply`, `sync`, and `archive`. Customize project context in `apps/<app>/openspec/config.yaml` so agents know the tech stack and conventions.

To onboard an app that already has real behavior (init + workflow-first baseline spec + roadmap companion in one pass), use [`opsx-bootstrap/README.md`](opsx-bootstrap/README.md). Interactive guide to the whole system and this repo's adaptation (app/spec stages + tags): [`docs/2026-07-10_openspec-guide/index.html`](docs/2026-07-10_openspec-guide/index.html).

Sanity-check after init:
```bash
cd apps/<app> && openspec list && openspec validate --all; cd -
```
Commit the new `openspec/` tree: `chore(<app>): initialize OpenSpec store (core profile)`.


## CLI reference (agent-usable)
Run from the app directory (`cd apps/<app>`) or pass the path:
| Command | Purpose |
|---------|---------|
| `openspec list` | List active changes |
| `openspec status --change <name>` | Artifact completion for a change |
| `openspec validate --all` | Validate specs and changes |
| `openspec archive <change>` | Sync deltas + move to archive |

Human-run (one-time per app): `openspec init`. Agent-run during work: list, status, validate, archive.


## Coexistence with `docs/` planning docs
- **`docs/`** — roadmap, meta, cross-app planning, dated decision docs.
- **`openspec/specs/`** — living per-app spec of *current behavior* (requirements + scenarios).
- **`openspec/changes/`** — per-feature intent (proposal → design → tasks) with an audit trail on archive.

Use OpenSpec for real feature work on opted-in apps; keep ad-hoc plan docs for everything else until the trial proves the ceremony is worth it.
